## 一、项目定位与使用场景

### 1.1 项目定位

SeatVerse 面向大学校园中的讲座、公开课、社团分享会、校园音乐会和学生论坛。系统解决传统报名只有「参加或不参加」、座位分配依赖人工、现场签到缺少统一记录等问题。

| 用户角色 | 主要任务 | 核心价值 |
|---|---|---|
| 活动参与者（普通用户） | 查找活动、查看场馆、选择座位、完成预约、查看电子票、到场出示二维码 | 快速找到感兴趣的活动并获得明确座位 |
| 活动主办方 | 创建活动、查看预约名单、管理活动状态、**扫码核验与签到** | 降低报名和座位分配的人工成本，入场核验有据可查 |

**关于第三个角色**：原设计中的「现场工作人员」在第一版**并入主办方**。主办方一人承担「发布活动」与「现场核验」两类职责。这样权限矩阵只需两套，降低权限复杂度；答辩口径为「主办方承担现场核验，权限矩阵已覆盖」。

### 1.2 第一版聚焦的场景

第一版固定为：一个学生社团举办约 100—150 个座位的校园讲座。主办方发布活动并使用预设场馆；参与者浏览活动、进入场馆、选择座位并预约；系统生成电子票与二维码；主办方扫码完成签到。该场景已覆盖核心业务，不需要真实支付或第三方票务接入。

| 角色 | 起点 | 关键步骤 | 终点 |
|---|---|---|---|
| 普通用户 | 活动列表 | 查看详情 → 进入场馆 → 3D 选座 → 确认预约 | 电子票与个人预约记录 |
| 主办方 | 主办方后台 | 创建活动 → 绑定场馆 → 查看名单 → 管理状态 → 扫码核验 | 可运营的活动与签到记录 |

### 1.3 判断标准

现场可以创建或打开活动、选择座位、完成预约、查看电子票；主办方可查看名单并扫码核验。3D 画面服务于这些任务，而不是替代业务流程。

## 三、技术选型（已定稿）

### 3.1 定稿结论

| 层 | 选型 | 关键理由 |
|---|---|---|
| 前端 | **Svelte 5 + Vite + shadcn-svelte + Threlte**（不使用 SvelteKit） | Threlte 是 Three.js 的 Svelte 声明式封装，3D 选座最省心；产物极小，低配演示机压力低；runes 状态管理零依赖 |
| 后端 | **Python 3.13+ / FastAPI** | 自动生成 OpenAPI 与 Swagger UI，接口文档零成本；Pydantic 在服务边界拦下字段错误；语法简洁，成员可互换；部署一条命令 |
| 数据库 | **SQLite**（标准库 `sqlite3`，WAL 模式） | 单文件，演示机零安装；换一台电脑也能跑；事务与唯一约束直接可用于防重复占座 |
| 种子数据 | JSONL 录入后导入 SQLite | 座位坐标手写 JSONL 最方便，导入后由数据库统一管控 |

**不引入 ORM**：repos 层只写 SQL。三点是理由：① 贴合分层规范「repos 只处理 SQL」；② `sqlite3` 随 Python 自带，无原生模块编译风险；③ ORM 查询结果类型大量退化为 `Any`，与「禁止 Any」的类型规范直接冲突。

### 3.2 选型过程中的关键取舍

| 维度 | 结论 |
|---|---|
| 前端为何不选 Flutter | Flutter 生态没有 Three.js 级别的成熟 3D 方案，若要 3D 只能降级为 2D 平面图或走 iframe 双栈，7 周内风险过高 |
| 后端为何不选 Java Spring Boot | 业务最稳、文档最好写，但样板代码多、启动慢，前两周进度会明显拖慢 |
| 后端为何不选 Express | 与前端同为 TypeScript 本可共用类型，但本组后端定为 Python；且事务与并发需全部手写 |
| 后端为何不选 Rust Actix | 工期风险最大，编译慢，通常仅 1 人能写，形成单点风险 |
| **数据库为何不用 JSONL 当主库** | P0 要求「10 个并发请求抢同一座位只有 1 个成功」，这条考的就是事务与唯一约束。SQLite 白送，JSONL 要自己实现文件锁、原子写与崩溃恢复，等于把送分题做成手写难点 |

### 3.3 系统架构与接口先行

| 层次 | 内容 |
|---|---|
| 用户端 | 普通用户端（活动、选座、我的预约、电子票）、主办方端（活动管理、名单、核验） |
| 前端应用层 | Svelte 5 单页应用，路由自选，Threlte 负责 3D |
| 后端服务层 | FastAPI，按 authentication / events / venues / seats / bookings / tickets 拆分模块 |
| 数据层 | SQLite 单文件，固定座位与每场活动的座位状态分开存储 |

**接口先行原则**

- 先画三个核心页面原型：活动列表与详情、选座、个人预约与电子票。
- 先约定活动、座位、预约、票务接口的字段与错误码。
- 3D 组件用模拟数据开发，接口完成后只替换数据来源，不改交互。

**协作工具**：Git + GitHub/GitLab 做分支协作、代码评审与问题追踪；接口文档由 FastAPI 自动生成并导出归档。

## 四、数据库设计与业务状态

### 4.1 数据表（八张）

| 数据表 | 主要用途 | 关键字段 | 设计说明 |
|---|---|---|---|
| users | 用户资料与角色 | 编号、姓名、邮箱、密码散列、角色、创建时间 | 角色区分普通用户与主办方 |
| venues | 场馆名称与布局配置 | 编号、名称、布局配置、容量 | **第一版只有一行** |
| seats | 场馆中的固定座位及位置 | 编号、场馆编号、排号、座号、x/y/z、座位类型 | 记录固定空间位置 |
| events | 活动信息与状态 | 编号、标题、简介、开始结束时间、主办方编号、场馆编号、状态 | 状态需限制可用转换 |
| event_seats | 某场活动中各座位的可用状态 | 编号、活动编号、座位编号、状态、版本号 | 同一座位在不同活动中拥有独立状态 |
| bookings | 用户预约记录 | 编号、活动编号、用户编号、状态、创建时间、取消时间 | — |
| booking_seats | 一次预约对应的座位 | 编号、预约编号、活动编号、座位编号、是否有效 | 支持一次预约多个座位 |
| tickets | 电子票与签到 | 编号、预约编号、票号、是否已核验、核验时间、核验人 | 票号唯一，已核验不可重复签到 |

**关键关系**：固定座位与每场活动的座位状态必须分开管理。A101 在周一讲座中已预约，在周五活动中仍可空闲；`seats` 存固定位置，`event_seats` 存每场状态。

### 4.2 状态转换

| 对象 | 主要状态转换 | 约束 |
|---|---|---|
| 座位 | 空闲 → 已预约；已预约 → 空闲（取消成功） | 只能由后端事务修改，前端颜色仅作提示 |
| 预约 | 已预约 → 已取消；活动结束后 → 已完成 | 取消须由本人、在活动开始前且未核验时发起；活动结束只影响展示态 |
| 电子票 | 未核验 → 已核验 | 已核验不能再次签到 |
| 活动 | 草稿 → 已发布 → 进行中 → 已结束；草稿 → 已取消 | 主办方不能修改不属于自己的活动 |

> 说明：活动“进行中/已结束”与预约“已完成”是按时间派生的展示态，不写入 `status`；存储值见 `docs/contracts/enums.md` §2.7。

### 4.3 单场馆约束

第一版只支持一种场馆：主办方创建活动时场馆控件保留但**只有一个可选项**，`venue_id` 字段在数据库与接口中完整保留。

| 保留什么 | 怎么保留 |
|---|---|
| 表结构 | `venues.id`、`seats.venue_id`、`events.venue_id` 原样保留，外键照建 |
| 取场馆的方式 | 服务端查库取唯一那一行，禁止写死场馆编号为常量 |
| 活动的场馆绑定 | 创建活动时把场馆编号照常写入活动记录，不是留空 |
| 接口形态 | 场馆接口照常用复数资源与编号路径，不因只有一条就改成单例路径 |

扩展多场馆时只需往 `venues` 加行、给下拉多塞选项，不需要改表、不需要回填历史数据。**带来的简化**：省掉场馆切换、多场馆适配、布局编辑器三块工作量，3D 只需适配一套坐标。

## 五、防止重复占座（本项目最值得答辩展示的工程问题）

两名用户几乎同时点击同一座位时，如果只在前端判断「空闲」，两个请求都可能看到旧状态并同时成功。前端状态只能用于交互提示，最终能否预约必须由后端和数据库决定。

### 5.1 SQLite 下的三个坑与对策

| 坑 | 对策 |
|---|---|
| SQLite 没有行级锁语句，常见 ORM 的行锁写法在其上无效或报错 | 不引入 ORM，手写 SQL，**禁止使用行锁写法** |
| 默认事务在读阶段不加锁，两个请求可同时读到空闲，随后双双写入 | 事务**一开始就申请写锁**，杜绝并发读到旧状态 |
| 只判断「当前是否空闲」仍会漏 | 用**条件更新**把「空闲」写进更新条件并判断受影响行数；同时用唯一索引兜底 |

### 5.2 事务流程

| 步骤 | 用户 / 前端 | 后端 | 数据库 |
|---|---|---|---|
| 1 | 选择座位并点击确认 | 接收活动编号、座位编号与用户身份 | — |
| 2 | 提交预约请求 | 开启事务，校验活动状态与座位归属 | 读取座位当前状态 |
| 3 | 等待结果 | 若座位仍可用，创建预约与座位关联 | 条件更新将座位改为已预约；唯一索引兜底 |
| 4 | 显示成功或失败 | 提交事务并生成电子票；已被占用则回滚并返回明确错误 | 写入票务记录或保持原状态 |
| 5 | 刷新座位状态 | 返回最新状态 | 前端重新读取座位状态 |

### 5.3 服务端必须验证的规则

- 用户不能取消其他人的预约。
- 普通用户不能创建活动；主办方不能修改不属于自己的活动。
- 已经核验的票不能再次签到。
- 已经结束或已关闭预约的活动不能继续预约。
- 一次预约涉及多个座位时，要么全部成功，要么全部失败。

**必须覆盖的测试用例**：两人同时预约、重复提交、取消后重新预约、重复签到、多座位预约失败回滚。不要只在前端隐藏按钮。

### 5.4 并发验收脚本

对已启动的服务发起 10 个**真并发 HTTP 请求**抢同一座位，断言 1 个成功（200）、9 个失败（409），且库中该座位状态为已预约。用真并发请求而非协程假并发——协程对文件锁测不出真实竞争。

## 六、六人分工与协作规则

按功能模块负责，而不是简单分成三人前端、三人后端。3D 选座是相对独立的技术模块，需指定明确负责人。

| 组员 | 主要职责 | 必须交付的成果 |
|---|---|---|
| A 项目负责人 | 需求分析、原型、任务管理、公共前端、我的预约与电子票、集成 | 需求规格说明书、页面流程、集成版本 |
| B 前端开发 | 活动列表、详情、登录、通用界面（主题与表单） | 可运行的用户端页面 |
| C 3D 开发 | 场馆模型、座位生成、点击选座、状态展示 | 独立可用的选座组件 |
| D 后端开发 | 用户认证、活动管理、权限校验 | 认证与活动相关接口 |
| E 预约与数据库 | 数据库设计、预约事务、取消规则 | 预约接口、数据库脚本、关键测试 |
| F 主办方端与质量保障 | 主办方后台、电子票核验、测试与部署 | 管理页面、测试报告、可运行部署版本 |

这不是六人各自独立开发后最后才合并。A、B、C 涉及前端，需统一组件规范；D、E 涉及后端，需统一接口与数据库约定。需求分析、数据库设计、测试、文档和答辩材料由全组共同参与。

**协作规则**

1. 每个模块都有负责人和至少一名协作成员。
2. 所有功能通过 Git 分支与合并请求进入主干，不能等到最后一周才集成。
3. 每周至少一次集成演示；从 S3 开始优先在真实接口上联调。
4. 接口字段、错误码、角色权限与数据库命名在文档中维护，修改时同步通知相关成员。
5. 前后端类型检查零错误为合并门槛，不允许用忽略注释绕过。

## 九、风险清单

| 风险 | 应对方式 | 检查点 |
|---|---|---|
| 3D 场馆建模耗时过长 | 第一版只做一个固定场馆，程序生成简化座椅与编号，不做整座建筑建模，不做拖拽式编辑器 | S2 末前必须有可运行的简化场馆 |
| 前后端接口对接过晚 | S1 确定字段与错误码；S2 用模拟数据并行开发；S3 开始真实联调 | 接口文档随改随更新 |
| 预约状态管理不一致 | 座位、预约、票务状态由后端统一校验，数据库事务负责最终写入，前端不承担业务裁决 | 覆盖并发、重复提交、取消与签到测试 |
| SQLite 库级写锁导致并发演示卡顿 | 开启预写日志与锁等待超时；演示并发控制在 10 请求内；说辞：写锁串行化正是防重的正确性来源 | S3 现场跑并发脚本 |
| 演示机无网或环境缺失 | 依赖版本锁定 + 离线依赖包；数据库为标准库自带；S7 彩排验证换机部署 | S7 |
| 各自开发最后才合并 | 每周至少一次集成演示，统一代码规范、分支策略与环境配置 | 从 S3 起每周锁定一个可运行版本 |
| 有人用 `Any` 或忽略注释绕过类型检查 | 类型检查器开启对应禁止开关；扫描脚本拦截；设为合并门槛 | 每次合并请求 |
| 核验时摄像头不可用 | 核验页必须支持手动输入票号，彩排两条通道都跑 | S7 |
| 被质疑「只有两个角色 / 只有一个场馆太简单」 | 答辩说明：主办方承担现场核验；多场馆与自由建模属 P2，场馆编号字段完整保留，扩展无需改表 | 答辩 |
| 忽视课程考核要求 | 尽早确认 UML、设计模式、测试方法、覆盖率与报告格式 | 把要求映射到交付物清单与时间线 |
