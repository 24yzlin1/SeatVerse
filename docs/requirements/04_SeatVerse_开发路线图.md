## 零、决策基线

### 0.1 技术栈（不变）

后端 **Python + FastAPI**，前端 **Svelte 5**，数据库 **SQLite**。此项自首轮定稿后未变更。

### 0.2 两份规范如何套用到 Python 后端

《后端开发规范》以 TypeScript 编写，其中**语言无关的架构精神全部照搬**，语言专属条款做等价替换：

| 规范条款 | 是否适用 | 本项目的 Python 落地 |
|---|---|---|
| 四层架构与依赖方向 | **完全适用** | 照搬四层，改用 Python 目录 |
| 参数校验在 scope、业务规则在 core、SQL 在 repos、类型在 types | **完全适用** | 照搬，一层不许越界 |
| 统一响应体、HTTP 恒 200、数字 `code` | **完全适用** | 与语言无关，照搬 |
| 禁止相对路径跨目录引用 | **完全适用** | 改为 Python 绝对导入 |
| `tsconfig.json` 严格开关、`.js` ESM 后缀、`@/` 别名 | 不适用 | 替换为类型检查器严格模式与绝对导入，见第六节 |
| 校验工具 `asBody` / `parsePositiveInt` | 精神适用 | scope 层自建等价校验工具 |

《前端开发规范》为 Svelte 5 编写，**完全适用**，无替换项。

### 0.3 沿用此前已定稿的决策

| 项 | 结论 |
|---|---|
| 数据库 | SQLite 单文件；种子数据用 JSONL 录入后导入 |
| 角色 | 只保留两种：普通用户、主办方（策划书「现场工作人员」并入主办方） |
| 二维码 | 从 P1 提前到 P0 |
| 接口前缀 | `/api/...`，不带版本号 |
| 鉴权命名 | 一律 `authentication` 全名，禁止 `auth` 缩写 |
| 场馆 | 第一版只支持一种场馆，场馆选择控件保留但只有一个可选项；`venue_id` 字段在数据库与接口中完整保留 |
| 响应契约 | HTTP 状态码恒 200，业务状态由响应体数字 `code` 承载 |

**数据库为什么不用 JSONL**：P0 验收要求"10 个并发请求抢同一座位只有 1 个成功"，这条考的是事务与唯一约束——SQLite 直接提供，JSONL 需自己实现文件锁、原子写与崩溃恢复，把送分题变成手写难点。JSONL 保留一个用途：种子数据的录入格式，导入 SQLite。

## 一、后端四层架构落地

规范定义入口层（`main`）→ `scope` → `core` → `repos` → `types`，依赖自上而下。本项目按此执行，不采用 `router / service` 划分。

| 层 | 目录 | 本项目落地内容 | 禁止事项 |
|---|---|---|---|
| 类型定义 | `app/types/` | 数据行类型（八张表的行结构）、请求/响应 DTO、统一响应结构 | 禁止 `Any`；禁止放运行时逻辑 |
| 数据访问 | `app/repos/` | 数据库连接、建表与索引、全部 SQL、CRUD | 禁止业务判断；禁止把驱动原始行对象外传 |
| 业务逻辑 | `app/core/` | 注册登录、活动状态流转、预约事务与防重、取消、票号生成、核验签到 | 入参必须是已校验的 DTO，禁止再收原始字典或重复做类型断言 |
| 路由控制 | `app/scope/` | 参数校验与归一化、鉴权与角色守卫、统一响应包装 | 禁止写 SQL；禁止返回非 200 状态码 |

**入口**：`main.py` 装配中间件与路由（沿用现有入口，不建 `index.py`）。

### 1.1 目录结构（初期扁平）

```
backend/
├── app/
│   ├── types/
│   │   ├── common.py            # 统一响应结构、分页结构
│   │   └── <领域>.py            # 数据行类型 + 请求/响应 DTO
│   ├── repos/
│   │   ├── db.py                # 连接、PRAGMA、BEGIN IMMEDIATE、行映射工具
│   │   └── <领域>.py            # 纯 SQL
│   ├── core/
│   │   ├── common.py            # 业务异常、领域规则工具
│   │   └── <领域>.py            # 业务用例
│   └── scope/
│       ├── common.py            # 校验工具、响应包装、异常处理
│       └── <领域>.py            # 路由与依赖
├── main.py                      # 应用装配入口（沿用现有入口，不建 index.py）
├── tests/
├── scripts/
│   ├── seed.py
│   └── concurrency_test.py
├── pyproject.toml            # uv 依赖与 poe 任务（不另建 requirements.txt）
└── .env.example
```

各层内**初期扁平**，不按领域建子目录；当某层文件超过 6 个或出现明显领域聚集时再按领域拆，且**必须四层对称拆分**。

**导入**：一律绝对导入，从 `app.` 起写全路径，禁止用相对导入跨层引用（对应规范"禁止 `../`"）。

### 1.2 规范与 Python 实现的三处等价替换

| 规范（TypeScript） | 本项目（Python） | 说明 |
|---|---|---|
| 校验在 scope 层手写 `asBody` | 请求体结构由类型注解模型自动校验，业务性校验与归一化（去空格、正整数范围、场馆合法性）仍写在 scope 层 | 结构校验自动化后，scope 只保留"业务性"校验，职责不减 |
| 中间件往请求对象挂 `userId` | 用依赖注入返回 typed 身份对象 | 避免在请求对象上挂无类型属性 |
| `ResponsePayload<T>` 泛型接口 | 泛型响应模型 | 保留泛型，避免 `Any` |

### 1.3 为什么不引入 ORM

`repos` 层只写 SQL，直接用**标准库 `sqlite3`**，不引入 ORM。三点理由：

| 理由 | 说明 |
|---|---|
| 贴合规范 | 规范明确 repos 只处理 SQL，ORM 会把查询逻辑上移，破坏分层 |
| 演示机零安装 | `sqlite3` 随 Python 自带，无需编译原生模块，换机演示风险最低 |
| 类型干净 | ORM 的查询结果类型大量退化为 `Any`，与"禁止 `Any`"直接冲突；手写行映射可以做到全链路类型明确 |

代价是行结果需手工映射，这项成本集中在 `repos/db.py` 一处，由 E 维护。

## 三、接口契约

### 3.1 统一响应体

严格按规范：所有接口 **HTTP 状态码恒为 200**，响应体字段固定三个。

| 字段 | 类型 | 说明 |
|---|---|---|
| `code` | 整数 | `200` 表示成功，其余为错误码 |
| `message` | 字符串 | 可直接展示给用户的中文提示 |
| `payload` | 对象 / 数组 / null | 业务数据；失败时按场景置空或给出最小上下文 |

前端只判断响应体顶层的 `body.code === 200`（**不是** `payload.code`），其余一律展示 `message`。列表数据统一包分页结构，含条目数组、总数、当前页、每页条数四个字段。

**注意**：前端请求客户端不能再依赖 HTTP 状态码做分支，401 也会以 HTTP 200 返回；令牌过期由响应体 `code === 401` 触发跳登录。

### 3.2 命名铁律

- 路径段与业务标识一律使用完整单词，禁止缩写；鉴权模块用 `authentication`，不用 `auth`。
- 路径不带版本号，统一以 `/api` 开头。
- 资源名用复数（`events`、`bookings`、`tickets`、`venues`），动作性接口用动词子路径（`cancel`、`verify`）。
- 后端错误码与前端错误码常量两处必须一致，同一次提交内同步。

### 3.3 M1 用户登录与认证

| 方法 | 路径 | 说明 | 权限 |
|---|---|---|---|
| POST | `/api/authentication/register` | 注册即登录，默认注册为普通用户；返回与登录同构的 `{token, user}` | 公开 |
| POST | `/api/authentication/login` | 登录，返回访问令牌与用户角色 | 公开 |
| GET | `/api/authentication/me` | 当前登录用户信息 | 登录 |

主办方账号不开放自助注册，由种子数据预置——避免任何人都能创建活动。

### 3.4 M2 活动查看

| 方法 | 路径 | 说明 | 权限 |
|---|---|---|---|
| GET | `/api/events` | 活动列表，支持关键词、状态筛选与分页 | 公开 |
| GET | `/api/events/{id}` | 活动详情 | 公开 |
| POST | `/api/events` | 创建活动（默认草稿），入参含 `venue_id`（可选项，前端可不传，服务端兜底绑定唯一场馆） | 主办方 |
| PATCH | `/api/events/{id}/status` | 发布 / 关闭预约 / 取消 | 归属主办方 |
| GET | `/api/venues` | 场馆列表，**第一版恒返回 1 条**，即唯一预设场馆 | 公开 |
| GET | `/api/venues/{id}/seats` | 该场馆全部座位的静态坐标（排号、座号、x/y/z、座位类型） | 公开 |

创建活动时场馆控件照常存在，但下拉只有一个可选项，界面以只读或单选项形式展示场馆名称；提交照常携带 `venue_id`，服务端校验其等于唯一预设场馆，传其他值直接拒绝。

### 3.5 M3 3D 选座与预约

| 方法 | 路径 | 说明 | 权限 |
|---|---|---|---|
| GET | `/api/events/{id}/seats` | **3D 选座的唯一动态数据源**，返回该场活动的座位状态 | 公开 |
| POST | `/api/bookings` | 提交预约，入参为活动编号与座位编号数组 | 登录 |
| POST | `/api/bookings/{id}/cancel` | 取消预约，座位恢复可预约 | 归属本人 |

### 3.6 M4 我的预约与电子票

| 方法 | 路径 | 说明 | 权限 |
|---|---|---|---|
| GET | `/api/bookings/me` | 我的预约列表，分页返回；页面按状态分组（待参加 / 已取消 / 已签到） | 登录 |
| GET | `/api/bookings/{id}/ticket` | 电子票详情，含票号、座位、活动与二维码内容 | 归属本人 |
| GET | `/api/tickets/{ticket_code}` | 用票号直查电子票（**票号直达页**：扫码或手动输入票号后进入；二维码内容即票号原文，非 URL） | 登录 + 本人票 |

> 两个票务读取接口都校验票据归属：非本人票统一返回 `404`，与“不存在”同一文案，避免用票号枚举探测（见 §3.8 的防枚举例外）。

### 3.7 M5 主办方核验端

| 方法 | 路径 | 说明 | 权限 |
|---|---|---|---|
| GET | `/api/events/{id}/bookings` | 本场活动的预约名单 | 归属主办方 |
| POST | `/api/tickets/verify` | 核验票号并写入签到 | 登录 + 主办方（仅本活动票） |

### 3.8 错误码表（数字，与规范一致）

| code | 含义 | 触发场景 |
|---|---|---|
| 200 | 成功 | — |
| 400 | 请求或业务规则不允许 | 参数缺失/类型错/取值非法；场馆编号不是唯一预设场馆；活动已结束或已关闭预约；取消时活动已开始或已结束 |
| 401 | 身份问题 | 未登录、令牌过期、账号或密码错误 |
| 403 | 权限问题 | 角色不足（普通用户访问主办方接口）、操作不属于自己的活动或预约（**票号/票据的归属校验除外**，见下文“防枚举例外”） |
| 404 | 资源不存在 | 活动、预约、座位、票号不存在；**票号/票据归属校验失败也归入本码** |
| 409 | 状态冲突 | **座位已被占（并发抢座失败）**、重复取消、重复签到 |

**场景细分靠 `message` 文案**，后端给出可直接展示的中文，前端原样弹出。需要前端做特殊分支的只有一处：**选座提交收到 409 时刷新座位状态并提示重选**。并发脚本断言"1 个 200、9 个 409"，无需解析文案。

**票号类资源的防枚举例外**：`GET /api/bookings/{id}/ticket`、`GET /api/tickets/{ticket_code}`、`POST /api/tickets/verify` 在「票号或预约不属于当前用户」「票不属于本主办方活动」时，统一返回 `404`，与「不存在」使用同一句 `message`；`403` 只保留给「已登录但角色不足」。理由：票号是随机串，若 403/404 可区分，等于提供枚举探测的判据。本例外与 02 号 §三 的对应段落一致。

## 五、数据设计与防重复占座

### 5.1 数据表（沿用策划书八张表）

| 数据表 | 用途 | 关键字段 |
|---|---|---|
| users | 用户与角色 | 编号、姓名、邮箱、密码散列、角色、创建时间 |
| venues | **仅一行**：唯一预设场馆 | 编号、名称、布局配置、容量 |
| seats | 该场馆的固定座位及空间坐标 | 编号、场馆编号、排号、座号、x/y/z、座位类型 |
| events | 活动信息与状态 | 编号、标题、简介、开始结束时间、主办方编号、场馆编号、状态 |
| event_seats | **每场活动的座位状态** | 编号、活动编号、座位编号、状态、版本号 |
| bookings | 预约记录 | 编号、活动编号、用户编号、状态、创建时间、取消时间 |
| booking_seats | 一次预约对应的座位 | 预约编号、活动编号、座位编号、是否有效 |
| tickets | 电子票与签到 | 编号、预约编号、票号、是否已核验、核验时间、核验人 |

**核心关系**：固定座位与每场活动的座位状态分开存。同一个 A101 座位在周一讲座中已预约，在周五活动中仍可为空闲。

### 5.2 单场馆约束

| 约束 | 说明 |
|---|---|
| `venues` 表固定只有一行 | 由种子脚本写入，接口层不提供场馆的创建、修改与删除 |
| 创建活动时保留场馆控件，但只有一个可选项 | 入参照常携带 `venue_id`，服务端校验其等于唯一预设场馆 |
| `seats` 表只属于这一个场馆 | 座位坐标、排号座号一次录入，所有活动共用 |
| 每场活动的座位状态仍需初始化 | 活动发布时按 `seats` 批量生成 `event_seats` 行，状态全为空闲 |
| 场馆管理界面不做 | 无场馆列表页、无场馆编辑页、无拖拽式布局编辑器 |

**编号字段全部保留**：`venues.id`、`seats.venue_id`、`events.venue_id` 照常保留，外键照常建立。区别只在"表里只有一行数据"，而不是"把场馆概念从模型里删掉"。

| 保留什么 | 怎么保留 |
|---|---|
| 表结构 | 三张表的场馆编号字段原样保留，不做任何裁剪 |
| 取场馆的方式 | 服务端查库取唯一那一行，禁止在代码里写死场馆编号为常量 |
| 活动的场馆绑定 | 创建活动时把传入（或兜底查到的）场馆编号写入活动记录，字段照填，不是留空 |
| 座位归属 | 座位照常带场馆编号，查询按编号关联，不是去掉关联裸查 |
| 接口形态 | 场馆接口照常是复数资源与编号路径，不因为只有一条就改成单例路径 |

扩展多场馆时，只需往 `venues` 加行、给创建活动下拉多塞选项，不需要改表、不需要回填历史数据。

**带来的简化**：省掉场馆切换、多场馆适配、布局编辑器三块工作量，3D 组件只需适配一套坐标。

### 5.3 驱动与连接

用**标准库 `sqlite3`**，同步连接。三条连接级约定必须落在 `repos/db.py`：

| 约定 | 作用 |
|---|---|
| 预写日志模式 | 读不阻塞写，降低并发演示时的卡顿 |
| 外键约束开启 | SQLite 默认不检查外键，不开等于外键白建 |
| 锁等待超时（建议 15 秒） | 抢不到写锁时等待而非立刻报错 |

### 5.4 防重复占座（本栈最大技术点）

SQLite 有三个必须绕开的坑：

| 坑 | 对策 |
|---|---|
| SQLite 没有行级锁语句，行锁写法在其上无效或报错 | 手写 SQL，**禁止使用行锁写法** |
| 默认事务在读阶段不加锁，两个请求可同时读到空闲，随后双双写入 | 关闭驱动的自动事务，事务**一开始就申请写锁**，杜绝并发读到旧状态 |
| 只判断"当前是否空闲"仍会漏 | 用**条件更新**把"空闲"写进更新条件并判断受影响行数；同时用唯一索引兜底 |

事务流程固定五步，全部在服务端一个事务内完成：

1. 校验活动处于可预约状态（未结束、未关闭）。
2. 创建预约记录。
3. 逐个座位执行条件更新：仅当该座位在该活动中仍为空闲时才改为已预约，判断受影响行数，不为 1 即视为被抢走。
4. 写入预约与座位关联记录、生成电子票与票号。
5. 任一步失败则整体回滚，返回 409「座位刚刚被预约，请重新选择」。

多座位预约的"要么全成功要么全失败"由同一事务与回滚保证。取消时把关联记录置为无效并把座位状态改回空闲，座位即可被重新预约。

**并发验收脚本**（S3 现场跑，放在 `scripts/concurrency_test.py`）：对已启动的服务发起 10 个**真并发 HTTP 请求**抢同一座位，断言 1 个 200、9 个 409，且库中该座位状态为已预约。用真线程而非协程——协程对文件锁测不出真实竞争。

### 5.5 全同步约定

端点一律用**同步函数**定义，数据库调用全部同步。框架会把同步端点放到线程池执行，因此不会阻塞事件循环。

**严禁**用异步端点配同步数据库调用（会阻塞事件循环）。这条写进仓库说明与评审检查项，用一条自动检查禁止同步数据库调用出现在异步端点中。

## 六、类型与静态检查规范（本轮新增重点）

### 6.1 后端：类型检查器严格模式

后端启用**严格模式**的类型检查器（mypy 或 pyright 选其一，全组统一，不混用），核心开关：

| 开关 | 要求 | 影响 |
|---|---|---|
| 严格模式总开关 | 必开 | 打开下面绝大部分检查 |
| 禁止未标注的函数 | 开 | 所有函数必须有完整参数与返回类型标注，含测试脚本 |
| 禁止调用未标注函数 | 开 | 第三方无标注库需补类型存根或本地声明 |
| 禁止显式 `Any` | 开 | 显式写 `Any` 直接报错 |
| 禁止泛型 `Any` | 开 | 容器不写泛型参数直接报错 |
| 禁止隐式可选 | 开 | 默认值为空的参数必须显式标为可选 |
| 禁止返回 `Any` | 开 | 返回无类型值直接报错 |
| 未使用的忽略注释报错 | 开 | 多余的忽略注释也算错，从源头杜绝随手加 |
| 禁止不完整的定义 | 开 | 部分标注视为未标注 |

`mypy` 注意：其 `--strict` **不包含**"禁止显式 `Any`"，需单独开启对应开关；pyright 在 strict 下默认已包含。统一配置写在配置文件里，不靠命令行参数传递，避免各人命令不一致。

### 6.2 禁用清单（评审逐条查）

| 禁用项 | 说明 |
|---|---|
| `Any`（显式、隐式、泛型均含） | 一律禁止，含函数返回值与类型别名 |
| `# type: ignore` | 一律禁止；确属第三方库缺陷时，改为在 `types/` 下补最小类型存根，并在合并请求说明理由 |
| 无类型断言绕过检查 | 禁止用类型转换把无类型值直接变成业务类型 |
| `getattr` / 字典下标取值当业务对象 | 边界处必须走显式构造或类型守卫 |
| 忽略注释无编号形式 | 即使需要抑制，也必须写明具体错误码，禁止裸忽略 |

由静态检查与自定义扫描共同执行：**类型检查零错误 + 扫描无禁用项**为合并门槛。

### 6.3 类型边界处理（无类型值只在边界出现一次）

| 边界 | 处理方式 | 归属层 |
|---|---|---|
| 请求体与查询参数 | 结构由请求模型在框架层自动校验；业务性校验（去空格、正整数范围、场馆合法性）由 scope 层校验工具完成，产出 typed DTO | `scope/` |
| 数据库返回值 | `repos/` 内统一做一次「驱动行 → 数据行类型」的显式映射，字段逐个取值并校验，**对外只暴露 typed 结果**；禁止把驱动行对象或原始元组外传 | `repos/` |
| 令牌解析结果 | 鉴权依赖内校验载荷结构并转成 typed 身份对象，禁止在业务代码里解析令牌 | `scope/` |
| 异常 | 异常处理器内用类型守卫区分业务异常与未知异常，未知异常统一记日志并返回通用错误，禁止把未知对象当业务错误读字段 | `scope/` |
| 第三方库缺类型存根 | 优先装官方存根包；确实没有则在 `types/` 下写最小存根文件，**不得用 `Any` 兜底** | `types/` |
| 配置读取 | 配置模型内完成类型转换与校验，业务代码只消费 typed 配置对象 | `types/` |

**关于框架自带的类型校验**：请求模型的自动校验发生在进入函数之前，core 层收到的就是已校验实例，这与规范"core 不做入参校验、只做业务规则判断"一致。core 层**不做**重复的结构校验，但**照常做**业务规则判断（活动是否已关闭、座位是否已被占、是否本人资源）。

### 6.4 前端类型要求

| 项 | 要求 |
|---|---|
| 编译器开关 | 严格模式开启；索引访问检查建议开启——取座位数组元素时必须处理可能为空的情况 |
| `any` | 一律禁止，含显式与隐式 |
| 忽略注释 | 一律禁止 |
| 非空断言 | 仅限已由路由守卫保证的字段，且需在类型声明处收口，不得散落各处 |
| 组件属性 | 用类型化的属性声明 |
| 接口响应 | 请求客户端内做一次响应解析与守卫，对外返回 typed 结果；禁止把接口返回直接断言成目标类型 |
| 组件库组件 | 生成代码不修改；自定义封装在 `common/components/` 内做类型收口 |
| 3D 组件 | 事件与网格参数使用库提供的类型 |

### 6.5 检查门槛

开发期与提交前各跑一次全量类型检查，**前后端均零错误**才算通过；类型检查未通过的代码不允许合并。S7 彩排前在干净环境再跑一次完整检查，确认演示机上的依赖与类型状态一致。

## 七、3D 选座的接口契约

M3 的 3D 组件只依赖两个接口，不直接连接数据库，这是 C 与其他人解耦的前提。

| 接口 | 用途 | 调用时机 |
|---|---|---|
| `/api/venues/{id}/seats` | 拿全部座位的**静态坐标**（排号、座号、x/y/z、座位类型） | 进入选座页取一次，可缓存 |
| `/api/events/{id}/seats` | 拿该场活动座位的**动态状态**（空闲 / 已预约） | 进入时取一次，提交失败后刷新 |

两个接口按座位编号对齐：静态坐标决定"摆在哪里"，动态状态决定"什么颜色"。坐标不变、状态高频变化，刷新时不必重传整套坐标。

| 事项 | 约定 |
|---|---|
| 坐标来源 | 全部由后端给出，前端不做布局计算，直接摆放 |
| 颜色映射 | 空闲灰、已预约红、本地已选绿 |
| 本地已选 | 只是交互态，不写库，提交时才做原子校验 |
| 失败处理 | 收到 409 后刷新座位状态并提示重选 |
| 开发期 | S2 用本地模拟数据开发，接口就绪后只替换数据来源 |
| 单场馆 | 只有一套坐标，镜头与灯光参数一次调好即可复用 |

**接口契约在 S2 末冻结**，之后只允许新增字段，不允许改字段含义。

## 八、二维码电子票与核验方案

| 环节 | 方案 |
|---|---|
| 票号生成 | 服务端在预约成功时生成，使用不可猜测的随机串（URL 安全），写入电子票表并设唯一约束 |
| 二维码内容 | 票号本身（20 位纯字符串，非 URL），前端用二维码库渲染到画布 |
| 出示方 | 用户在「我的预约 → 电子票」页展示二维码，同时展示明文票号 |
| 扫码方 | 主办方在核验页调用摄像头扫码，解析出票号后调核验接口 |
| 兜底通道 | 核验页必须支持**手动输入票号**——演示机摄像头不可用时仍能完成演示，这是硬性要求 |
| 重复签到 | 服务端条件更新 + 唯一约束双保险：已核验的票再次核验返回 409，并回显首次签到时间 |
| 有效期 | 核验时校验活动状态与预约状态：已取消的预约、已结束的活动不允许签到 |
