## 一、项目理解与安排依据

### 1.1 这次要完成什么

第一版服务于一个约 100—150 座的校园活动场馆，只有普通用户、主办方两种角色。必须完成的业务链是：

1. 参与者注册或登录，浏览和搜索活动，查看详情。
2. 进入 3D 场馆，选座并提交预约，服务端防止重复占座。
3. 查看个人预约与二维码电子票，按规则取消预约。
4. 主办方创建、发布和管理自己的活动，查看名单，扫码或输入票号签到。
5. 重复签到、越权操作、已关闭活动预约等情况被服务端正确拦截。

技术沿用 Svelte 5 + Vite + shadcn-svelte + Threlte、FastAPI、标准库 sqlite3；不增加支付、实时多人同步、自由场馆建模或多场馆切换。JSONL 只用于种子数据录入，SQLite 是业务主库。

## 五、S2 必须冻结的契约与规则

以下含原文约束和本方案补充建议；补充规则用于明确开发边界，不代表用户已经逐条确认业务细节。

1. **响应码**：HTTP 恒为 200，响应体为 `{ code, message, payload }`。成功检查 `body.code === 200`，座位冲突检查 `body.code === 409`；不能检查 `body.payload.code`。修正原文中“返回 409”的歧义，测试同时检查 HTTP 200 和业务码分布。
2. **登录与权限**：普通注册不能传角色提权；票号本身不赋予查看别人电子票的权限；主办方只能核验自己活动的票。此处对原文宽泛的“主办方可核验”作归属收紧建议。
3. **活动与预约规则**：建议将“关闭预约”与“活动结束”区分，前者停止新预约但不废止有效票。建议取消只允许在活动开始前且尚未核验时进行；S2 由 A、D、E、F 将确定的状态枚举与规则写进接口示例。
4. **重复请求**：建议重复座位编号入参返回业务码 400；已占座或重复取消返回 409；同一用户可预约不同座位，原请求重复提交不得再次占用或生成新票。不引入额外的实时锁座和支付流程。
5. **数据标识**：静态坐标与动态座位按 `seat_id` 对齐；接口样例必须包含编号、活动／场馆关联、状态和坐标。仅本地选中不写库。
6. **数据库约束**：固定场馆和座位独立于活动；`event_seats` 的活动／座位组合唯一，有效预约座位的活动／座位组合唯一。历史取消记录保留，唯一约束必须允许取消后重新预约。
7. **票与并发**：建议一次预约对应一张包含全部所选座位的票。取消和核验均在统一写事务中重查状态，不能出现“已取消仍签到”。票号唯一用于身份区分，重复签到由票状态的条件更新保证。
8. **工程约定**：沿用 uv、mypy 和 npm 锁文件；后端业务端点用同步 `def`。A、B 在 11/6 前选定适配当前工程的路由方案；C、F 分别验证 3D、二维码与扫码依赖，再由 A 协调锁文件。

所有接口在 11/8 前归档至少一份成功、失败和权限示例。S3 起兼容新增字段，改字段含义必须同步所有调用方与测试。

## 七、协作、评审与文件边界

1. **任务粒度**：每项任务写明主责、验收动作和依赖，尽量拆为 0.5—2 天可展示的成果。不要使用“负责前端”等无交付边界的任务名称。
2. **分支与集成**：每项功能走短分支和合并请求。建议每周三做一次中途联调、周日做验收；出现阻塞当天报告，超过一个工作日由备份成员加入。
3. **评审搭档**：前端 A／B 互审，C 的页面由 B 审、座位契约由 E 审；D／E 互审，F 的后端由 D 审、页面由 A 审。作者不能作为唯一验收人。
4. **公共文件**：A 维护路由、请求客户端与前端锁文件；B 维护通用界面和主题；D 维护后端入口与异常；E 维护数据库和 schema；F 维护票务。新增依赖由模块负责人提交理由和验证结果，再由配置负责人同步锁文件。
5. **合并检查**：前端执行现有 `check`、`lint` 和 `build`；后端执行 mypy 与相关 pytest；新增禁止项扫描和同步端点检查由 A 统筹、D 提供后端规则。修复当前脚手架配置后再把检查设为门槛，不预先宣称其通过。
6. **检查范围**：目前后端 `check` 仅指向 `app`，后续应由 A、D 纳入入口、测试和脚本。每个负责人补齐自己新增函数的类型；不靠 `Any` 或忽略注释过关。
7. **交接最小集**：负责人提交代码位置、接口样例、启动方式、测试结果和已知问题，备份成员至少操作一次该模块。
